# Отчёт: Узкие места при миграции монолита на микросервисы — «Медикаменте»

## Введение

Компания «Медикаменте» планирует миграцию устаревшей монолитной системы на современную микросервисную архитектуру. Цель — поддержать пятикратный рост объёма данных, расширение команды и открытие новых филиалов. В процессе перехода необходимо выявить потенциальные узкие места, которые могут негативно повлиять на работоспособность нового решения.

Метод анализа — диаграмма Исикавы («Рыбья кость») по пяти категориям: Инфраструктура, ПО и архитектура, Интеграция, Персонал, Процессы.

---

## 1. Инфраструктура

### Выявленные проблемы

| Проблема | Риск |
|---|---|
| Физический сервер в офисе — единственная точка отказа | Полный простой при сбое оборудования. Нет отказоустойчивости и резервирования |
| Файловый режим 1С — блокировки при росте числа пользователей | Зависание при более 10 одновременных подключениях. Невозможность горизонтального масштабирования |
| Общий диск — узкое место по I/O при 5× росте данных | Деградация скорости чтения/записи. Конкуренция за доступ между сотрудниками |

### Рекомендации

| Рекомендация | Приоритет |
|---|---|
| Перенос инфраструктуры в облако (Yandex Cloud) или приватный ЦОД. Развёртывание Kubernetes-кластера с автоматическим масштабированием узлов | **P0** |
| Миграция 1С из файлового режима в клиент-серверный (на PostgreSQL). Последующая декомпозиция на сервисы платежей и склада | **P0** |
| Замена общего диска на S3-совместимое хранилище (MinIO) с шифрованием и политиками доступа | **P1** |

## 2. ПО и архитектура

### Выявленные проблемы

| Проблема | Риск |
|---|---|
| Excel используется как база данных | Потеря целостности данных, отсутствие транзакционности, гонки данных при одновременном редактировании |
| Монолит без API-слоя | Невозможность независимого масштабирования компонентов. Сложность декомпозиции на микросервисы |
| Нет доменного разделения данных | Доступ «ко всему» из любого компонента. Смешение медицинских, платёжных и складских данных в одном контексте |

### Рекомендации

| Рекомендация | Приоритет |
|---|---|
| Перенос данных из Excel в PostgreSQL с реляционной моделью. ETL-пайплайн для миграции исторических файлов | **P0** |
| Внедрение API Gateway (Kong) и декомпозиция монолита на домены: CRM, записи, платежи, склад, медицинские карты | **P1** |
| Разнесение данных по отдельным схемам/базам с Row-Level Security. Внедрение DataHub для каталога данных | **P1** |

---

## 3. Интеграция

### Выявленные проблемы

| Проблема | Риск |
|---|---|
| OLE-интеграция ККМ ↔ 1С — устаревший протокол | Блокировки, невозможность горизонтального масштабирования. Зависимость от Windows-компоненты |
| Новый API лаборатории анализов | Контракт может не покрывать категории данных. Риск утечки через API. Один пациент может увидеть данные другого |
| Платёжный шлюз — новая связь в системе | Рассинхронизация платежей, задержки, потеря транзакций при сбоях |

### Рекомендации

| Рекомендация | Приоритет |
|---|---|
| Замена OLE на REST API. ККМ через фискальный шлюз. Очередь событий (Kafka / Redis Streams) для асинхронной обработки | **P1** |
| OpenAPI-контракт с тегами конфиденциальности. OPA-политики на каждый эндпоинт. Тестирование на доступ к чужим данным | **P1** |
| Асинхронная интеграция через message broker. Idempotency-ключи. Ретраи с exponential backoff. Dead-letter queue для сбойных транзакций | **P2** |

## 4. Персонал

### Выявленные проблемы

| Проблема | Риск |
|---|---|
| IT-команда — 3 человека. Не хватит ресурсов на миграцию | Срыв сроков, перегрузка, ошибки из-за спешки. Технический директор — единственный архитектор |
| Новые сотрудники не знают контекст legacy-систем | Ошибки при работе со старой логикой. Долгий онбординг |
| Нет DevOps-практик в команде | Ручные релизы, высокий риск человеческой ошибки. Долгое время восстановления при сбое |

### Рекомендации

| Рекомендация | Приоритет |
|---|---|
| Найм 2–3 backend-разработчиков и DevOps-инженера. Постепенная миграция по доменам, а не «большим взрывом» | **P0** |
| Документирование As-Is перед миграцией. Onboarding-гайды по каждому домену. Парное программирование при онбординге | **P2** |
| Внедрение CI/CD (GitLab CI), автоматических тестов, blue-green деплоя. Infrastructure as Code (Terraform) | **P1** |

---

## 5. Процессы

### Выявленные проблемы

| Проблема | Риск |
|---|---|
| Ручной ввод данных во всех процессах | Кратный рост ошибок при 5× нагрузке. Зависимость от конкретных сотрудников |
| Двойной учёт платежей (Excel + 1С) | Рассинхронизация данных. Расхождения в отчётах. Время на сверку |
| Нет регрессионного тестирования | Поломки при миграции не выявляются вовремя. Релизы «вслепую» |

### Рекомендации

| Рекомендация | Приоритет |
|---|---|
| Автоматизация записи пациентов через портал. Валидация на уровне API. Минимизация ручного ввода | **P0** |
| Единый источник истины в PostgreSQL. 1С работает как read-only потребитель через API. Ликвидация Excel-дублирования | **P1** |
| Тестовый стенд с синтетическими данными. Контрактные тесты (Pact). Нагрузочное тестирование перед каждым релизом | **P1** |

---

## Сводный план по приоритетам

### P0 — критично, выполнить до начала миграции

1. Перенос серверной инфраструктуры в облако / Kubernetes
2. Найм backend и DevOps-разработчиков
3. Миграция данных из Excel в PostgreSQL
4. Перевод 1С в клиент-серверный режим
5. Автоматизация записи пациентов через портал

### P1 — параллельно с миграцией

6. API Gateway (Kong) + декомпозиция монолита на домены
7. Замена OLE на REST API для ККМ
8. CI/CD, автотесты, Infrastructure as Code
9. Устранение двойного учёта платежей
10. MinIO вместо общего диска

### P2 — после стабилизации

11. Платёжный шлюз с message broker
12. Onboarding-документация для новых сотрудников

## Заключение

Диаграмма Исикавы выявила 15 узких мест в пяти категориях. Ключевые риски связаны с физическим сервером без отказоустойчивости (P0), файловым режимом 1С (P0), Excel как базой данных (P0) и нехваткой IT-команды (P0). Без устранения P0-рисков приступать к миграции нельзя — это приведёт к простоям и потере данных.

Рекомендуемый подход — поэтапная миграция по доменам: сначала запись пациентов и CRM, затем платежи, затем склад и интеграции. Каждый этап — с автотестами, нагрузочным тестированием и откатным планом.
